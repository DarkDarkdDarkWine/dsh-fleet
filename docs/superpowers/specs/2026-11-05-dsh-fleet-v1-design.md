# dsh-fleet v1 设计

- 日期：2026-11-05
- 状态：草案，待确认
- 取代：v0.3.x（共享密钥 + 单管家 + 手工名册）。v1 不兼容 v0.3。

标注约定：**【用户定】** 是讨论中用户明确决定的；**【提议·已认可】** 是我提出、用户同意的；**【审阅后·我定】** 是审阅时发现的缺口，由我做的判断，用户可以推翻；**【实现者定】** 是留给实现者判断的；**【待定】** 是还要问用户的。

---

## 1. 意图

让同一网络里多台设备上的 DSH 互相通信：每台设备上的 agent 能给其他设备的 agent 派活、收结果，不设主节点。

起点是用户在 Hermes 上的一套简易 A2A：以 NAS 为主力，通过 Telegram 对话。v1 要把它做成**可以发布给别人用的独立 DSH 插件**，有完整的用户体验：自动发现、安全入网、心跳和状态监控、配置、CLI。【用户定】

用户自己的用法：NAS 上的 agent 维护 NAS，PC 上的 agent 帮忙操作 PC。但产品不限定用途，由用户自己定义。【用户定】

两个代表场景：

1. **故障转交**：Mac 上的 agent 调用 NAS 上的搜索服务报错 → 改用自己的搜索工具，把手头任务做完 → 同时让 NAS 上的 agent 排查原因 → NAS 回报 → Mac 上的 agent 向用户汇报，等用户决定 → 用户决定后再让 NAS 去修（NAS 要记得自己刚才的诊断）。
2. **同步记忆**："你们几个同步一下记忆"。一个 agent 逐台去联系其他设备。v1 只能用文字完成；传文件放到后面的阶段。

## 2. 目标、非目标、反目标

### 目标（v1）

- 舰队有自己的编码；成员靠身份识别，不靠地址【用户定】
- 局域网内自动发现新设备；在任意一台成员设备上用 PIN 确认后，全舰队都认可它【用户定】
- 关键操作用舰队 PIN 验证"是本人"，AI 不能使用 PIN【用户定】
- 每台设备一个 agent，带一段身份描述，其他 agent 靠它决定找谁【用户定】
- 派活是一问一答；接收方给每个来源对话单独开一个对话【用户定】
- 心跳和状态监控；面板同时覆盖设备健康、任务追踪、故障排查【用户定】
- 回执自动回到发起任务的那个对话，并通知用户【提议·已认可】
- 对方离线时先存着，等它上线再送达【提议·已认可】
- 配套 CLI【用户定】

### 非目标（不在 v1 范围）

- 内网穿透。跨网络由用户自己解决，例如用 tailscale；插件只要求设备之间能连上【用户定】
- 多 agent 协同：任务拆解、调度编排、共享记忆。那是另一个产品【用户定】
- 群聊（多个 agent 和人在同一个房间里），放到后面的阶段【用户定】
- 传文件，放到后面的阶段【用户定】
- 插件自带"群发并汇总"：agent 想通知几台设备就逐台派活【提议·已认可】
- 长任务进度提醒（v0.3 有）：去掉，进度在面板里看【提议·已认可】
- 中心服务器、云端中继、账号体系

### 反目标（即使能跑也算失败）

- AI 通过舰队工具就能自己授予信任：比如未经人输入 PIN 就把一台设备加进舰队（防护范围见 §2.5）
- 成员之间日常通信，依赖一个全舰队通用、在网络上传输的长期凭据（v0.3 共享密钥的问题）。入网时 PIN 经过加密通道传输一次，不算违反这一条（§5.4）
- 某台设备成为单点：它离线，其他设备之间就不能通信
- 在局域网里以明文传输任务内容
- 插件让 DSH GUI 白屏或进入安全模式（客户端代码在任何路径上都不许抛错）

## 2.5 安全定位【用户定】

**够用就行，不是生产级产品。** PIN 只用来验证"是本人在操作"。

- **要防的**：
  - AI 通过舰队自己的工具授予信任；
  - 网页等内容里的提示词注入诱导 AI 授予信任；
  - 同一局域网里有人旁听任务内容；
  - 同一局域网里其他舰队的设备混进来。
- **明确不防的**：
  - 能执行 shell 的 agent。它和用户本人等价：可以运行本机 CLI、读取本机令牌和私钥。文档和 README 里要写明这一点；
  - 被盗设备上的 PIN 校验值被离线破解。6 位数字 PIN，破解是现实可行的；
  - 入网时被冒充的舰队骗走 PIN。

## 3. 约束（来自 DSH 平台，已查证）

- **v0.3 的现状（GLM 侧实测）**：
  - NAS 用 `dsh --profile nas --no-open --host 100.85.254.124 --port 43129` 绑定**一个具体的 Tailscale IP**，这是 rc.5 `--host` 的官方用法（"one concrete IPv4 or IPv6 literal"）。因此局域网设备连不到它，只有 tailnet 内部能访问；而且对 tailnet 暴露的是整个 DSH Web 面，不只是 `/fleet/*`。
  - 桌面版只监听 127.0.0.1，用户没有可传的启动参数，所以只能"拉取"回执、收不到任务。
  - Tailscale 分配的 100.x 地址是长期稳定的，除非设备被删掉重新加入。
- **DSH 自带 Web 服务拒绝监听 0.0.0.0。** 实测报错：`--host 0.0.0.0 is an unspecified (wildcard) address, which is not supported`。 `@deepseek-ai/dsh-host-webserver` 0.2.1-rc.5 的配置校验原话："binding every interface would expose remote code execution to the network"。桌面版默认只监听 127.0.0.1。因此**舰队协议不能挂在 DSH 的 Web 服务上，插件要自己开一个监听端口**（§5.2）。DSH Web 服务只承载本机的面板和本机控制接口。
- 无头会话没人替它选模型，创建或恢复会话时必须给 `agentOptions:{provider, model}`，否则报 `prompt variable "{{model}}" has no value`（v0.3 踩过）。
- 工具挂载靠 setup 回调里 `await agentPresets.mount(agentCtx, presetId)`；setup 必须返回 void（框架会对返回值调用 `.commit()`）。
- 客户端半体：桌面版（0.2.1-rc.2）通过 `dsh.client.inject: ["@deepseek-ai/dsh-client-ui-slots"]` 加 `ctx.inject(["slots"], …)` 注册面板，不能直接访问 `ctx.slots`；rc.5 没有这个包时静默跳过。`apply()` 任何路径都不许抛错。
- 桌面版不热加载 profile 的 `cordis.patch.yml`，改动要重启应用。
- DSH home 不一定是 `~/.dsh`（桌面版在 `~/Library/Application Support/dsh-desktop/harness`），所有路径从 `$DSH_HOME` 推导。
- peer 依赖 `@deepseek-ai/cordis ~4.0.5`。
- 同一台设备可以跑多个 DSH 实例（v0.3 在 Mac 上用两个 profile 做过联调），身份因此跟着**实例**走，不跟硬件走（§5.1）。
- **平台**【审阅后·我定】：v1 必须支持 macOS、Linux、Windows。用户自己就有一台 Windows PC，NAS 是 Linux。对 Docker 里的 DSH：bridge 网络会挡住 mDNS 组播，所以走"手动填地址"入网，文档里说明可以改用 host 网络。密钥和令牌文件的保护在 Windows 上用 ACL，不用 0600。防火墙引导覆盖三个平台。测试矩阵覆盖三个平台。

## 4. 路线

讨论过三条，用户选了**路线二**。

| 路线 | 做法 | 取舍 |
|---|---|---|
| 一、在 v0.3 上逐步改造 | 保留现有接口、工具、CLI、面板，逐个替换核心 | 每一步都能用；但身份、名册、会话模型、回执流向几乎全要换，最后只剩外壳，一路背着兼容代码，`index.js` 已有 870 行 |
| **二、重写 v1，自有协议，按模块拆分（选定）** | 新协议；身份、发现、成员、投递、会话对接、面板各成模块；不兼容 v0.3 | 结构干净、可测；前期工作量最大，切换时几台设备一起升级；v0.3 的平台经验全部保留 |
| 三、重写 v1，消息部分按 Google A2A 标准 | 信任和发现自己做，任务和"名片"按 A2A | 能和外部 A2A 智能体互通；要照标准实现整套接口，标准还在变；A2A 不解决信任和发现 |

选路线二的理由：这个产品最难、也最有价值的部分是信任、发现和离线送达，A2A 帮不上；目前只需要 DSH 之间通信；以后要互通可以加一个 A2A 网关，和群聊、传文件一起放到后面的阶段；现在的使用者只有用户自己的设备，没有必须兼容的外部用户。

## 5. 设计

### 5.1 概念

- **舰队**：一个独立的信任域。由第一台设备"创建舰队"时生成：
  - **舰队编码**：随机 128 位，界面上显示短形式；
  - **舰队名**：给人看的；
  - **舰队 PIN**：用户自己设定。
  
  同一个局域网可以同时存在多个舰队，靠舰队编码区分【用户定】。
- **成员**：一个运行 dsh-fleet 的 DSH 实例。正常情况是一台设备一个，但多实例天然支持【提议·已认可】。
- **成员身份**：成员首次启动时**自己生成**一对 Ed25519 密钥，私钥永远不离开本机；成员编码 = 公钥指纹。舰队给这个身份签发**成员证书**，记录成员编码、公钥、显示名、加入时间、签发者。用户看到的是"舰队给了你一个身份"，实际上身份即使被人知道也无法冒用【提议·已认可】。
- **地址**：只当作"现在在哪"的线索，不参与识别（§5.6）【用户定】。
- **舰队 PIN**：只用于关键操作时验证"是本人"，平时通信不用它；AI 不能使用；丢了是用户自己的事，但留有重置路径（§5.5）【用户定 + 提议·已认可】。

### 5.2 网络层：独立监听端口

- 插件用 `node:http(s)` 自己开一个 TCP 端口（默认端口号【实现者定】，必须能配置），只提供舰队协议，不暴露 DSH 的任何其他接口。这个端口不受 DSH Web 服务 `--host` 校验的约束，用户已确认可行。
- 绑定地址：默认所有网卡（0.0.0.0 / ::），可配置为指定地址。这一个设置同时解决三件事：
  - 桌面版也能收任务；
  - 一个端口同时覆盖局域网、Tailscale 和本机；
  - 地址变了也不受影响。
  
  这样做的安全前提是：这个端口上只有两类入口，一是双向认证过的成员通道，二是限流的配对入口；DSH 的 GUI、API 等能执行代码的部分完全不出网。
- 端口门禁【用户转述 GLM 建议，采纳】：配对入口有 PIN 锁定和按来源限速；所有请求都有请求体上限（v0.3 是 2MB，v1 沿用这个量级）。
- **传输加密 + 双向认证**：成员之间用 TLS，双方都出示由自己设备密钥生成的自签证书，对方用舰队名册里的公钥校验，不依赖任何 CA。局域网里的旁观者看不到任务内容【提议，本文档新增，实现者可以换成等价方案，但"加密 + 双向认证 + 只认名册内公钥"三条不可少】。
  - 不采用"默认靠 Tailscale 加密、纯局域网模式风险自负"的方案。理由：产品的主场景是没有 Tailscale 的局域网用户；Node 自带 TLS，代价不大；§2.5 把"局域网旁听"列在要防的范围里。
  - 入网时，新设备还没有对方的证书，所以那一次 TLS 只能防被动旁听，防不了冒充的舰队。这已经在 §2.5 列为不防的风险。
- 配对入口（§5.4）是唯一允许未认证连接访问的地方：限流，连续失败要锁定。
- **本机控制接口**：CLI 和面板通过 DSH Web 服务上的本机接口控制插件。面板使用 GUI 的登录态；CLI 使用配置目录里一个权限为 0600 的本机令牌文件。
- macOS 首次监听端口时会弹出"允许传入连接"的系统提示，需要在入门引导里说明。

### 5.3 成员名册与同步

- 名册是一份**签名事件日志**，事件包括：创建舰队、加入（签发证书）、移除、修改 PIN 校验值、更新身份描述（§5.8）。每条事件由一名成员用设备私钥签名；关键事件只有在该成员本机完成 PIN 校验后才会签发。
- 同步：心跳里携带名册版本摘要。两边不一致时，互相补齐缺少的事件。合并规则是并集；同一成员先后有"加入"和"移除"时，**移除胜出**。被移除的成员重新上线时会被拒绝，想回来只能重新入网。
- 其他成员认可一条事件，依据是"签名来自名册里的现有成员"，而不是 PIN。**由此接受的风险**：一台被攻破的成员设备可以不经 PIN 签发关键事件。可以接受的理由是：被攻破的成员本来就能在其他成员上执行命令。
- 没有主节点：任何成员都可以签发事件，日志通过成员之间的点对点同步扩散。
- **日志结构与移除规则**【审阅后·我定】：
  - 名册日志是哈希链接的 DAG：每条事件都引用签发者当时已知的最新事件。
  - "移除成员 X"这条事件生效后，X 签发的事件中，凡不是这条移除事件祖先的，一律拒收。这样被盗设备无法伪造"早于移除"的事件；它在移除之后签发的入网，也会自动失效，相当于自动连带移除。
  - 移除之前 X 已经签发、并且同步出去的入网，属于正常历史，保留；面板标出"由 X 批准入网"，方便用户顺手一并移除。
  - 两台设备在网络分裂期间同时修改 PIN：按确定规则取一个（时间戳较晚者胜，相同时比较成员编码），并通知用户"PIN 修改有冲突，以 Y 设备上那次为准"。

### 5.4 创建舰队与入网

**创建**：在第一台设备上，通过面板或 CLI 输入舰队名和 PIN，生成舰队编码，签发"创建"事件。

**入网**（新设备 N，现有成员 M）：

1. N 装好插件并启动。在局域网里，N 和各成员通过 mDNS 互相发现（服务名、库的选型【实现者定】）。广播内容只有舰队编码短形式、舰队名、成员显示名，不广播任何秘密。
2. 在 N 上，用户从发现到的舰队列表里选一个（列表显示舰队名和舰队编码的短形式），输入舰队 PIN。**只需要在新设备上输对 PIN，不需要现有成员再点"同意"**【用户定】。
3. N 与 M 建立加密连接（TLS），N 把 PIN 发给 M；M 在本机校验，失败要计数并锁定（§5.5）【审阅后·我定：按"够用就行"的定位，不用 PAKE】。
4. 校验通过后，M 签发 N 的成员证书（"加入"事件），并把完整名册交给 N；随后通过同步扩散到全舰队。
5. 所有成员的面板都会提示"新设备 N 已加入（由 M 批准）"，并提供一键移除。

讨论过、没有采用的方案：用现有成员生成的一次性邀请码代替 PIN 入网。它的好处是被盗设备破解出 PIN 后也无法再让新设备入网；代价是入网要在两台设备上操作。用户选择保留"在新设备上输 PIN"【用户定】。

**不在局域网里的入网**（例如只通过 tailscale 连接）：mDNS 不跨 tailscale。可以在 N 上手动填写某个成员的地址，再走同样的 PIN 配对。这是兜底路径，不是主路径。

### 5.5 关键操作与 PIN

- **PIN 的形态**：固定为 6 位数字【用户定】。移除成员时，面板提示"建议修改 PIN"，不强制【审阅后·我定】。
- **关键操作**：入网（在新设备上输 PIN）、移除成员、修改 PIN【提议·已认可】。
- **日常操作**（不需要 PIN，AI 可以使用）：派活、查目录和状态、查任务、修改本机的身份描述【提议·已认可】。
- **PIN 不经过 AI**【提议·已认可】：AI 工具只能**发起**关键操作，插件随后弹出它自己的确认框，由人输入 PIN（GUI 弹窗，或 CLI 里的隐藏输入）。发起的请求在面板里挂起，直到有人批准、拒绝，或者过期。PIN 绝不能出现在对话、工具参数或日志里。
- **挂起的关键操作可以在任意成员上批准**【审阅后·我定】：挂起请求作为消息扩散给全舰队，用户在任何一台有面板或 CLI 的成员上输入 PIN 都能批准，批准由那台成员签名。理由：NAS 这类无头设备上发起的请求，要能在 Mac 的面板上点批准，不能逼用户 SSH 进 NAS 去用 CLI。请求有有效期，过期自动作废。
- **本机校验**：每台成员只保存 PIN 的慢哈希校验值（算法【实现者定】，须为 scrypt/argon2 这一类），连续输错要锁定一段时间【提议·已认可】。修改 PIN 时把新的校验值作为名册事件同步出去。
- **重置**【提议·已认可】：在任意一台成员设备上，用本机 CLI 重置 PIN。依据是：能在这台机器上开终端，就等于拥有它的全部权限。重置同样作为签名事件同步出去。

### 5.6 发现与地址

- 局域网：mDNS 持续广播和监听，用于发现新设备，也用于更新已知成员的局域网地址。
- 每个成员在心跳里报告自己当前的全部地址和舰队端口（局域网 IP、tailscale IP 等），其他成员按成员编码更新记录，并持久化下来；联系时按"最近成功的地址优先"依次尝试【提议·已认可】。
- 设备在家里入网后，出门在外靠之前学到的 tailscale 地址联系。

### 5.7 心跳与状态

- 每个成员定期（间隔默认值【实现者定】，可配置）向已知成员发送心跳，内容包括：
  - 版本；
  - 当前地址列表；
  - 在线状态；
  - 正在处理的任务数和排队数；
  - 名册版本摘要；
  - 身份描述的版本。
- 判断离线：连续若干次心跳失败【实现者定】。离线超过一个阈值后通知用户（§5.10）。
- 心跳也承担离线送达的触发：发现对方重新上线时，立即补发待送的消息（§5.9）。

### 5.8 身份描述与舰队目录

- **身份描述由成员自己声明**，在这台设备上通过面板、CLI 或 AI 工具编辑，作为名册事件同步给全舰队；所有成员看到的是同一份。只有这台设备自己能改它【提议·已认可】。修改不需要 PIN。
- 内容 = **人写的部分**（显示名 + 一段自由文本：我是谁、我负责什么，类似技能描述）+ **自动采集的事实**（操作系统、主机名、DSH 和插件版本、在线和忙碌状态、可用工具概要）【提议·已认可】。这和 Grok Bot 的做法一致：名字、头衔、描述，agent 读描述决定找谁。
- **舰队目录对 AI 实时可见**：AI 查目录时拿到的是当下的成员、描述和状态。不能像 v0.3 那样把名册写死在工具说明里。

### 5.9 派活与回执

**派活**（发起方成员 S，接收方成员 R）：

- 派活内容是结构化的：**目标**、**必要背景**、**期望交付**，外加可选的**事务编号**。工具说明里明确提示：对方看不到你们的对话【提议·已认可】。
- 一问一答，不做来回追问【用户定】。R 缺少信息时，返回"信息不足"回执，写明缺什么，这次派活就此结束；S 补全信息后重新派一个完整的任务【提议·已认可】。
- **每件事一个对话**【用户定】：
  - R 用 (S 的成员编码, 事务编号) 确定一个本地会话：已经有就接着用，没有就新建；
  - 不带事务编号就开一件新事，生成新的编号并随回执返回；
  - S 上的 agent 想接着同一件事继续时，带上这个编号，就会回到 R 上的同一个会话，所以 R 记得之前的诊断。
- R 上的这些会话在 DSH GUI 里正常可见，标题写明来源和事由，例如"来自 mac：排查搜索服务故障"。使用本机的 agent 配置（provider、model、preset、cwd），挂载完整工具。
- **并发上限**：每台成员默认最多同时处理 2 件派来的事，超出的排队，上限可配置【提议·已认可】。
- **自动归档**：事务会话 7 天没有新动静就归档，天数可配置【提议·已认可】。
- **回执类型**：完成（附结果）、失败（附原因）、信息不足（附缺什么）。是否还需要"拒绝/繁忙"等类型【实现者定】。

**回执流向**【提议·已认可】：

- S 发出时记下发起的会话。回执一到，插件把它作为一条消息注入那个会话，并唤醒那里的 agent，由它向用户汇报；同时通知用户（§5.10）。
- 如果发起的会话已经关闭或归档，回执进入面板的待处理列表，并通知用户。
- 注入消息的形态（来源标记、措辞）【实现者定】，要能和用户本人发的消息区分开。

**离线送达**【提议·已认可】：

- 待送的派活和回执都存在发送方本地，可靠落盘，重启也不丢；对方重新上线后补发，失败按退避重试。
- 每条待送消息有有效期（默认值【实现者定】，例如 24 小时），过期后给发起的会话一张"失败：对方一直离线"的回执。
- 接收端按消息编码去重，所以重发不会导致重复执行。
- 因为每台成员都能被直接连上，v1 只做推送，加离线存储与重发；不再需要 v0.3 的"拉取"路径。
- 接收方在执行过程中重启：会话本身由 DSH 持久化，但执行到一半的处理方式【实现者定】。至少要保证发起方最终能收到一张回执，不会永远挂着。

### 5.10 面板与通知

- 一个面板，逐层点进去【提议·已认可】：
  1. **舰队首页**：每台成员一张卡片，显示在线状态、身份描述、版本、正在处理和排队的数量、最后心跳；另有待批准的关键操作、发现到但未入网的设备。
  2. **成员页**：这台成员收到和发出的任务列表及状态。
  3. **任务页**：任务的时间线（派出、送达、开始、回执），附错误信息；能跳转到本机对应的会话。
- 面板里的操作：创建舰队、加入舰队、批准或拒绝挂起的关键操作（都要输 PIN）、移除成员（输 PIN）、编辑本机身份描述、修改 PIN。
- **主动通知**【提议·已认可】：成员离线超过阈值、任务失败、回执到达但发起的会话已不在、有新设备加入或被移除、关键操作等待批准。具体的通知渠道（DSH 自带的通知能力，或者面板角标）【实现者定，先查 DSH 有什么】。
- 布局沿用"每台设备一个窗口、往来按时间线显示"的思路（借鉴 Grok Bot），具体视觉设计【实现者定】。

### 5.11 AI 工具

| 工具 | 作用 |
|---|---|
| `fleet_directory` | 实时的舰队目录：成员、身份描述、状态 |
| `fleet_send` | 结构化派活（目标/背景/交付/可选事务编号），立即返回；回执稍后自动回到本会话 |
| `fleet_task` | 查询某个任务的状态和时间线 |
| `fleet_describe_self` | 修改本机的身份描述 |
| `fleet_request` | 发起关键操作（移除成员等），只会生成一个挂起请求，等人输入 PIN 批准 |

工具命名和拆分【实现者定】，但"AI 不能完成关键操作"这一条不可少。fleet-ops 技能按 v1 重写。

### 5.12 CLI

覆盖面板的全部能力（命名【实现者定】）：创建舰队、加入舰队、状态、成员、批准、移除、修改 PIN、重置 PIN（仅本机）、派活、任务列表、任务详情、修改身份描述。PIN 用隐藏输入读取，不接受命令行参数，以免进入 shell 历史。CLI 只连本机插件（通过 §5.2 的本机控制接口），由本机插件代它和其他成员通信。

### 5.13 配置与本地数据

- 数据都放在 `$DSH_HOME/fleet/`（实例级）：设备密钥（0600）、名册日志、待送队列、任务记录、本机令牌。
- 用户可编辑的设置放在一个配置文件里，包括：
  - 监听端口和绑定地址；
  - agent 配置（provider、model、preset、cwd）；
  - 并发上限；
  - 归档天数；
  - 待送消息有效期；
  - 心跳间隔。
- 舰队成员信息**不**手写在配置里，全部来自名册。

### 5.14 从 v0.3 迁移

不兼容。用户的几台设备一起升级：在一台上创建舰队，其他设备逐台入网。v0.3 配置里的 `steward.provider/model/preset/cwd` 可以自动导入为 agent 配置。v0.3 的接口全部移除。版本号 1.0.0。

## 8. 需要先验证的平台能力

这些会影响实现，开工前要在 DSH 源码或运行时里查清楚；查不到的，要先想好替代方案再动手：

1. 插件能否给会话设置标题、能否归档会话
2. 插件能否把一条消息注入一个由 GUI 打开着的会话并唤醒 agent，以及这样做会不会和 GUI 冲突
3. DSH 有没有可供插件使用的用户通知能力
4. 桌面版里插件自行监听端口是否可行，包括 macOS 防火墙提示和应用沙盒的影响
5. 客户端面板能否弹出模态框，用于 PIN 输入
