## 规矩

1. **不碰产品代码**：不改 `lib/`、`bin/`、`test/`、`package.json`，也不改计划文件和设计文档。
2. **探针单独放**：所有探针代码放在仓库外的临时目录，或者做成一个单独的测试插件，例如 `dsh-fleet-probe`。用完要卸载，把用户的 profile 恢复原状。
3. **不动已装的版本**：NAS 和桌面上装的 dsh-fleet 0.3.x 及其配置，一律不能动。不发布任何东西到 npm。
4. **不泄露秘密**：不读也不打印 `fleet.json` 里的 secret、各类令牌和 API key。文档里如果出现这类值，一律打码。
5. **需要用户配合的就直说**：比如 macOS 防火墙弹窗要用户在屏幕前看，或者需要重启 Desktop。要先说清楚需要用户做什么、看什么，再继续。
6. **分清"实测"和"读源码"**：
   - 每项结论都要标明证据来源：【实测】还是【源码】。
   - 【源码】结论要写清文件路径和行号（取 DSH 安装目录或 node_modules 里的实际文件）。
   - 能实测的必须实测。

## 要查的 9 项

每项都要写清下面几块：**结论**（可行 / 不可行 / 部分可行）、**证据**、**对计划二、三的影响**；结论是否定的，还要写**替代方案**。

1. **Desktop 内置 Node 的版本**：在探针插件的 `apply` 里打日志，记录 `process.version`、`process.platform` 和 `process.arch`。同时记下 DSH Desktop 的版本，以及 harness 里 `@dsh/*`（或同等核心包）的版本。NAS 上的 DSH 也查一遍同样的信息。

2. **Ed25519 证书和双向 TLS**：
   - 用第 1 项那个运行时（不要用系统自带的 node）跑一个约 30 行的探针脚本，依赖装在临时目录：
     - 用 `@peculiar/x509` ^3.1.0 生成两张 Ed25519 自签证书；
     - 用 `node:https` 起服务，设 `requestCert: true, rejectUnauthorized: false`；
     - 客户端带上自己的证书去连。
   - 记录三点：
     - 握手能否成功；
     - 服务端能否用 `req.socket.getPeerCertificate()` 拿到对方公钥；
     - 客户端能否拿到服务端证书。
   - 如果失败，按计划 Task 0 Step 2 的降级方案（ECDSA P-256 做 TLS，用 Ed25519 背书）再跑一遍，并记录结果。

3. **插件自己开端口**：
   - 探针插件在 `apply` 里执行 `https.createServer(...).listen(43190, "0.0.0.0")`。
   - 从同一局域网（或 Tailscale）的另一台设备 `curl -k` 访问它。
   - 记录三点：
     - 能否监听成功；
     - 另一台设备能否访问到；
     - macOS 有没有弹"是否允许传入连接"（请用户观察），弹的是 DSH 还是 node。

4. **mDNS 互相发现**：
   - 两端都用 `bonjour-service` ^1.4.4：一端 `publish({ name, type: "dsh-fleet", port, txt })`，另一端 `find({ type: "dsh-fleet" })`。
   - 测 Mac ↔ NAS 双向发现，记录发现耗时、`txt` 能否完整传到，以及拿到的地址列表。
   - 要说明两台设备是在同一局域网直连测的，还是经 Tailscale 测的。mDNS 一般穿不过 Tailscale，这个预期内，测出来如实记录即可。

5. **会话管理（spec §8.1）**：插件能否做下面三件事，每件都要实测：
   - 新建一个会话，且这个会话出现在 GUI 的会话列表里；
   - 设置会话标题；
   - 归档会话。
   找到对应的 API 后写清调用方式；找不到就说明 GUI 里能看到什么、看不到什么。

6. **向打开着的会话注入消息（spec §8.2，最重要）**：
   - 用户先在 GUI 里打开一个会话。探针插件拿到它的 session id，然后执行：
     - `ctx.agents.resume({ resumeSessionId })`
     - `agent.followup(createUserMessage(...))`
   - 分三种情况各测一次：
     - a. 会话打开着、agent 空闲；
     - b. 会话打开着、agent 正在回答；
     - c. 会话没打开。
   - 每种情况记录：
     - GUI 里能否实时看到注入的消息；
     - agent 是否会被唤醒并回复；
     - 有没有报错、出现重复的 agent 实例、消息顺序错乱，或者 GUI 需要刷新才显示。
   - 如果 `resume` 不是正确入口，就去找正确的入口。

7. **用户通知（spec §8.3）**：DSH 有没有给插件用的通知能力，例如系统通知、应用内 toast、侧栏角标。
   - 也要试一下：客户端面板里的浏览器 `Notification` API 能不能用。
   - 两条路都不通的话，写清楚面板里还能用什么方式提醒用户。

8. **面板弹模态框（spec §8.5）**：
   - 用户输入 PIN 需要一个模态框。用和 v0.3 面板相同的挂载方式（`window.__ModuleLoader__` 或 `dsh-client-ui-slots`；参考 v0.3 的 `lib/client.js`）挂一个测试面板。
   - 试两种做法：
     - 用 portal 把内容挂到 `document.body`，看能不能做出覆盖全窗口的模态层；
     - 看 DSH 有没有现成的 dialog 组件可以用。
   - 再确认一点：面板里的输入框能不能正常拿到键盘焦点。

9. **dispose 钩子**：`ctx.on("dispose", fn)` 在插件卸载、重载和 DSH 退出这三种情况下是否触发。在钩子里关掉第 3 项的服务器，然后确认三点：
   - 重载后再 `listen(43190)` 不会报 EADDRINUSE；
   - 不关服务器直接重载，会不会出现端口被占用；
   - DSH 退出时端口是否释放。
